# Code Review — 2026-08-19

Security-focused review of the full current codebase of `swlib` (not diff-based). No prior `review/CODE_REVIEW_*.md` exists in this repo, so all findings below are new. See [`Docs/REVIEW.md`](../../Docs/REVIEW.md) for how findings in this file are tracked and marked fixed. Because every backend service depends on swlib, findings here are platform-wide.

Verified clean: crypto primitives are solid — Argon2id with OWASP-recommended parameters (`swlib/crypto/hashing.go`), `crypto/rand` used throughout (`hashing.go`, `keypair.go`, `random.go`, the one `math/rand` hit is in `svcreg/resolver.go` for load-balancing jitter, not security-relevant), constant-time comparison via `subtle.ConstantTimeCompare`, 3072-bit RSA keys for JWT signing. CORS wildcard+credentials misconfiguration is explicitly guarded (`app/grpc.go` `validateCORSOrigins`). Rate-limit interceptors correctly distrust client-suppliable headers and use real transport peer addresses. `Config.Parse` doesn't log secret values. No secrets found logged anywhere in the module.

### 1. `MimeType` middleware panics on any path without a dot

`swlib/http/middlewares/mimetype.go:22`: `r.URL.Path[strings.LastIndex(r.URL.Path, "."):]`. `strings.LastIndex` returns `-1` when there's no `.` in the path, so this slices `path[-1:]` and panics ("slice bounds out of range") on every request whose path has no extension — i.e. virtually all API/page routes (`/`, `/login`, `/api/users`, etc.). Go's `net/http` recovers per-connection panics so it degrades to a dropped connection/500 rather than a process crash, but any service that mounts this (it's documented as the recommended static-file-server middleware) would break on most requests and be trivially poundable for wasted CPU/goroutine churn. Currently not referenced by any service (only in a doc comment), so no live blast radius yet, but it's a landmine for the next adopter. Severity: High.

### 2. `jwt.VerifyToken` silently discards the error from claim mapping

`swlib/jwt/jwt.go:196-197`: `jwtClaims = &Claims{}; jwtClaims.FromMapClaims(mapClaims)` — the returned error is never checked, so `VerifyToken` can return `(claims, nil)` even when claim extraction failed partway through. This same finding was independently surfaced from three call sites — see [[authservice]] and [[swayrider-api]] reviews. In practice this fails closed today (an early return inside `FromMapClaims` leaves `SwayRiderClaims` nil, which `EndpointProfile.Evaluate`'s type switch then rejects via its `default: ErrInvalidJwt` case), so it isn't an authorization bypass as currently wired. But it's a real defect in a security-critical path — a silently swallowed error can mask future regressions (e.g. if the claims struct or evaluation logic changes) and makes debugging malformed-token issues opaque. Affects every service that verifies JWTs (all of them, via `jwtkeys.Cache.Verify` / `EndpointProfile.Evaluate`). Fix: propagate the error from `FromMapClaims`. Severity: Medium.

### 3. Shared `SourceInfo` HTTP middleware trusts `X-Forwarded-Proto`/`X-Forwarded-Host` unconditionally

`swlib/http/middlewares/source_info.go:66-74`: `getRequestSecure`/`getRequestHost` accept these headers from any caller with no trusted-proxy check, and the result feeds `cookies.NewCookieOptsFromContext` (governs the cookie `Secure`/`Domain` attributes). This is exactly the class of bug the codebase explicitly guards against elsewhere — `grpc/interceptors/clientinfointerceptor.go` has detailed comments on why `X-Forwarded-For` can't be trusted without a gateway boundary, and `swayrider-api/internal/middleware/auth.go` reimplements this same logic correctly with an `isTrustedProxy()` gate. `SourceInfo` is not currently invoked by any service (grep confirms zero callers, only referenced in its own doc comment), so there's no live exposure — but it's exported and documented as the recommended way to populate `security.SecureKey`/`HostKey` for the `cookies` package, so any future service that wires it up as documented inherits a spoofable "is this HTTPS" determination unless it duplicates swayrider-api's hardening. Severity: Medium (currently dead code).

### 4. `cookies` package is insecure-by-default

`swlib/http/cookies/cookie.go:82-88,135-146`: `NewCookieOpts()` and the no-opts path of `NewServerCookie`/`ClearCookie` default `Secure: false`. A caller only gets a `Secure` cookie by explicitly threading `NewCookieOptsFromContext` through a populated `security.SecureKey`. Checked actual usage: `swayrider-api/internal/handlers/auth.go` and `authservice/internal/server/authentication.go` do this correctly for `access_token`/`refresh_token`, so there's no live vulnerability today — but the shared constructor's default is the unsafe direction, which is a footgun for any new call site that forgets to pass context-derived opts. Severity: Low.

### 5. Archive extraction has no size/entry-count caps

`swlib/compression/tar.go` and `zip.go` correctly guard against zip-slip/tar-slip and symlink escape, but `UnTar`/`UnZip` impose no limit on total decompressed size or entry count, so a malicious/corrupt archive could exhaust disk or memory (classic zip-bomb) if ever run against untrusted input. Per the data pipeline being the likely consumer (operator-supplied data only, per project convention), exposure is limited, but worth noting since the package is general-purpose and exported. Severity: Low/Info.
